Case Studies

Six problems, start to finish.

Global insurance provider

2 weeks → 2–5 days

to build and run a risk model

A Modelling Framework for a Team That Didn't Have One

Problem: I joined an insurance risk pricing team as one of only two technical people. Models were assembled by hand — outputs written to Excel, groupings changed manually, code hard to reuse — so a single risk model took around two weeks.

Approach: designed and built a modelling framework from scratch: a modular, object-oriented Python pipeline covering processing, modelling, charts and tables, built so non-technical colleagues could run it too. Moved the team's code off shared drives and onto Git so others could develop on it.

Outcome: model turnaround fell to 2–5 days. Technical and non-technical colleagues have built 20+ risk models on it so far, and it can substitute Emblem for the team's needs. With modelling no longer the bottleneck, the work moved on to what the models say: rate drivers by product, cross-product comparisons, and a master baseline model.

WarrantyIT · Co-founder

RAG → VLM

PDF, printed and handwritten bills → structured JSON

RAG to VLM: A Pragmatic Pivot in Document Extraction

Problem: WarrantyIT needed to pull structured data out of real-world warranty bills — PDFs, printed and handwritten — and feed it straight into a claim form.

Approach: first explored a RAG pipeline with LangChain and Pinecone. It fell short on the messier, handwritten bills, so I pivoted to a vision language model — Moondream, with a planned migration to LLaVA — which gave higher accuracy across both printed and handwritten documents. Implemented it end to end.

Outcome: a VLM pipeline that outputs structured JSON directly into the frontend claim form. The point isn't the tool — it's picking the one that fits the problem over the one that's fashionable.

Global insurance provider

2 days → 5 minutes

to produce the views every rate review starts with

Automating the First Two Days of Every Rate Review

Problem: every rate review starts the same way — someone spends about two days hand-building one-way and two-way views of written and earned premium, loss ratios and fees before any analysis can begin. A colleague had started automating it, then left the company.

Approach: took it over and rebuilt it from scratch under a full project lifecycle: learned how a review actually runs, built the views by hand to understand them, designed and documented the tool, then automated it in Python — writing all of the code as the team's only technical resource.

Outcome: the same views now take five minutes. Six reviews are already running on it, another five are planned before the end of Q2 2027, and the design extends to the full product suite.

Professional sports analytics company

Data audit → delivery

injury risk projects, run end to end for clients

Injury Risk Analytics for Professional Sports Clients

Problem: professional sports organisations wanted to understand what drives injury risk across their athletes — usually with data of very uneven quality.

Approach: ran each project through three stages: a data health check to flag missing or invalid data and get it fixed with the client; descriptive analysis for EDA and feature selection; then XGBoost or SVM models with SHAP to explain what drives the risk. Worked with in-house specialists on each sport, and moved from running the pipelines to writing project documentation and presenting findings to clients myself.

Outcome: clients got an explained view of injury risk with answers to the questions in their brief, presented directly. I also proposed and rebuilt the ageing health check pipeline from scratch — runtime fell from about five minutes to two, and the new design included features that would otherwise have taken days of further development.

Global insurance provider · Middle East

No comparable data → live model

solo, from data strategy to implementation

Pricing a New Product with No Comparable Data

Problem: a new insurance product was launching in the Middle East. The provider already operated there, but had no data for a product of this kind — only data from the products it already sold in the region.

Approach: led the modelling end to end and entirely solo, from a data strategy built on the existing products' data through to pricing and risk recommendations.

Outcome: the model is being implemented in-market. I presented the risk profile and methodology at a global underwriting leadership townhall, where it was well received across the underwriting function.

University research centre · AI research

12–15 models

trained and deployed for live vision use cases

Putting a Real-Time Vision Engine to Work

Problem: a research group had built a real-time event processing engine for vision problems, and needed to show the world what it could do in practice.

Approach: designed and ran use cases across agriculture, smart cities, construction and tennis. One example: segmenting honeycomb images to separate honey-filled cells from the rest of the comb, to estimate a season's honey yield. Built the image and video datasets myself, trained or transfer-learned the models, and deployed them on the engine to run live.

Outcome: the use cases became peer-reviewed papers I co-authored and defended — ACM VLDB Endowment (2021) and IEEE Internet of Things Journal (2022).

Plus dashboards, AI agents, reporting automation, data engineering, and the two products I'm co-building.
